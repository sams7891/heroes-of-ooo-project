# Reading and editing the game

## Java reference versus editable code

`reference/java/` contains Java generated by JADX 1.5.6 from the confirmed
working APK. All **47 game-namespace classes** have a reference file. They are
useful for understanding names, conditions, and data flow, but they are not the
publisher's original source. JADX can reconstruct branches imperfectly and may
produce Java that does not compile. This reconstruction retains warnings in
methods such as `GameThread.onTouch`, `Actor.update...`, and `Room` methods.

The authoritative editable representation is **smali** in `decoded/smali/`.
Apktool assembles it into `classes.dex`, the Android bytecode executed by ART.
Changing a reference `.java` file alone does not change the APK.

For example:

| Read this | Edit this |
|---|---|
| `reference/java/com/globalfun/adventuretime/free/Actor.java` | `decoded/smali/com/globalfun/adventuretime/free/Actor.smali` |
| `reference/java/com/globalfun/adventuretime/free/Engine.java` | `decoded/smali/com/globalfun/adventuretime/free/Engine.smali` |
| `reference/java/com/globalfun/adventuretime/free/GameThread.java` | `decoded/smali/com/globalfun/adventuretime/free/GameThread.smali` |

Android Studio can browse these files, but this is an Apktool project. Its
normal Android Gradle Build button is not the build system for this package.
Use the included Python command from its terminal, VS Code, or another shell.

## Where the gameplay lives

The APK has 6,397 class definitions because it bundles many old SDKs. The game
namespace is `com.globalfun.adventuretime.free`, with **47 classes and 686
defined methods**. There are **no native methods in those game classes**.

These entry points were checked in the reconstructed code and DEX method table:

| Class | Responsibility and useful entry points |
|---|---|
| `Main` | Android activity and lifecycle; `onCreate`, `onPause`, `onResume`, `getResourceAsStream`, `vibrate`, `logMessage`; initializes ad/analytics integrations |
| `GameThread` | `SurfaceView`, input callbacks, rendering requests; `surfaceCreated`, `onTouch`, `onKey`, `runGameLoop` |
| `Engine` | Overall game state, loop, progression, inventory, saves; `run`, `updateTime`, `newGame`, `loadRoom`, `loadDungeon`, `hurt`, `heal`, `pickup`, `rmsRead`, `rmsWrite` |
| `Actor` | Finn, enemies, bosses, projectiles, movement, collisions and combat; `updateFinn`, `updateMonster`, `updateIceKing`, `doSword`, `doHammer`, `hit`, `move`, `testCollision` |
| `Animator`, `Sprite` | Animation state and sprite drawing; `animate`, `reset`, `setLoops`, `paint`, `paintTransformed` |
| `Dungeon`, `Room` | Loading maps/rooms, placing objects, transitions, tile drawing; `loadDungeon`, `loadOverworld`, `Room.load`, `enter`, `exit`, `paintRoom` |
| `UI` | Menus, HUD, dialogue, controls and transitions; `loadUI`, `paintHearts`, `paintMenu`, `openTalk`, `loadText`, `handleTouch` |
| `GameCanvas` | Shared rendering/input/resource/sound/save helpers; `createStream`, `pullByteArray`, `pullStrings`, `rmsRead`, `rmsWrite` |
| `Touch`, `Touch$TouchRegion` | Touch regions, virtual controls, drag handling and touch-state tracking |
| `Graphics`, `Image`, `CustomFont`, `Font` | Graphics wrappers, image decoding and font drawing |
| `Resources`, `Resources320`, `Resources480` | Resource filenames, indices and size-specific settings |
| `RecordStore` and related classes | J2ME-style record storage implemented using Android private files |

For a complete method inventory, see `reports/original-inspection.json`.

Typical flow: Android creates `Main`, which creates `Engine` and `GameThread`.
`GameThread.runGameLoop()` calls `Main.engine.run()`. Input callbacks feed the
engine; drawing flows through the game canvas, UI, room, sprite and graphics
helpers. This is a custom Java game. The packaged Unity-related classes are
advertising integrations; their presence does not make the game a Unity project.

## A first code edit: enable existing diagnostic logging

The original `Main.logMessage(String)` does nothing. Many lifecycle callbacks
already call it. Giving it a body provides an easy way to confirm that your
code changes are being compiled and executed.

Open `decoded/smali/com/globalfun/adventuretime/free/Main.smali`. Find the method
starting with `.method public static logMessage(Ljava/lang/String;)V`. Replace
that whole method, through `.end method`, with:

```smali
.method public static logMessage(Ljava/lang/String;)V
    .locals 1
    .param p0, "msg"    # Ljava/lang/String;

    const-string v0, "HeroesOfOooDev"
    invoke-static {v0, p0}, Landroid/util/Log;->d(Ljava/lang/String;Ljava/lang/String;)I
    move-result v0
    return-void
.end method
```

Rebuild:

```bash
python project.py build
```

After installing your locally signed APK, use Android Studio Logcat or:

```bash
adb logcat -s HeroesOfOooDev:D '*:S'
```

Put the app in the background and return to it. Existing calls such as
`Main.onStart()` and `Main.onStop()` should appear under that tag. On Windows
CMD, use `"*:S"` rather than single quotes. The patch is also supplied as
`examples/enable-logging.patch`; with Git installed, you can apply it from the
project root using `git apply examples/enable-logging.patch`.

This example was applied, rebuilt, and inspected during project preparation.
The downloadable `Main.smali` is restored to its original compatibility-build
state; applying the example is your first optional edit. Device execution of
this logging example has not been tested here.

## Smali essentials

| Syntax | Meaning |
|---|---|
| `Lcom/.../Actor;` | A class descriptor |
| `I`, `Z`, `V`, `[B` | `int`, `boolean`, `void`, `byte[]` |
| `hurt(I)V` | A method taking an int and returning void |
| `.locals 1` | One local register, `v0`; parameter registers are additional |
| `p0`, `p1` | Parameter registers; `p0` is `this` for an instance method |
| `const/4 v0, 0x1` | Put a small integer into a register |
| `iget` / `iput` | Read/write an instance field |
| `sget` / `sput` | Read/write a static field |
| `invoke-static`, `invoke-virtual` | Call a static or instance method |
| `move-result`, `move-result-object` | Obtain an immediately preceding call's result |
| `if-eqz`, `if-nez`, `goto` | Conditional or unconditional branches to labels |

Use the correct register type: a numeric value cannot stand in for an object
reference. `move-result...` must immediately follow the appropriate invocation.
Changing register counts can shift parameter registers if a method uses
`v` registers for parameters; prefer `p` names in your own edits. Some invoke
formats have register-number limits and require a `/range` form.

Search for a method's full descriptor when it has overloaded names. Start with
small edits and rebuild after each one. Apktool handles offsets and DEX
checksums; you should not manually calculate byte offsets when editing smali.

## Constants and gameplay changes

`Actor` has descriptive constants such as `BOMB_FUSE`, `DAMAGE_SWORD` and
`HERO_TICKS_RECOVER`. The original compiler may inline them into instruction
literals. Editing a `.field ... = ...` initializer alone might therefore have
no effect. Read the method that actually uses the value, locate the relevant
instructions, and change that use site deliberately.

For example, use `Actor.doSword`, `Actor.hit`, and the relevant update methods
when exploring sword damage. `Engine.updateTime` uses a 70 ms timing budget;
changing the timing can change gameplay speed because parts of the game use
ticks. Establish the timing/data model before changing global pacing.

## Asset changes

The two main sets are `decoded/assets/high/` and `decoded/assets/medium/`.
`Main` selects `Resources480` or `Resources320` from its calculated game canvas
size. Edit both size variants when appropriate, and preserve filenames and
dimensions until you understand the indexing/layout assumptions.

An easy visual experiment is a small change to `high/Splash.png` and its
`medium/Splash.png` counterpart. Keep PNG transparency and dimensions. Build
using either `build` or `build-assets`; the latter retains the original patched
game bytecode and only incorporates asset changes.

The `.bin` and `.cf` files are custom game data. Some include packed images,
maps, localized strings or font data. They are not all interchangeable archive
formats. Start with `GameCanvas.createStream`, its `pull...` methods,
`Main.getResourceAsStream`, `Main`'s image-decoding helpers, `Dungeon`, and
`Resources` before writing a data converter. `pullByteArray` reads a length
and payload; higher-level loaders determine each file's structure.

## Save files

`RecordStore` uses Android's `openFileInput` and `openFileOutput` to maintain
files named `recordStore<name>.dat`. These are private app data, not assets
inside the APK. `Engine.rmsRead` and `rmsWrite` interpret the game state inside
records. Repacking the APK does not copy the player's current progress into it.
